# AGENTS.md

## Область действия

Эти инструкции действуют для всего репозитория. Перед началом работы прочитайте этот файл и `soile-platform/README.md`.

## Цель проекта

SOILE — MVP платформы практических бизнес-задач для студенческих команд.

Обязательный сквозной сценарий:

1. Бизнес создаёт черновик задачи.
2. AI задаёт уточняющие вопросы и предлагает дополнения.
3. Бизнес редактирует и подтверждает карточку.
4. Система рассчитывает рейтинг готовности от 0 до 100.
5. Подтверждённая задача публикуется в общем каталоге.
6. Студенческая команда самостоятельно выбирает задачу и отправляет предложение.
7. Бизнес вручную принимает одну, несколько или ни одной команды.
8. Баллы команды начисляются только за подтверждённый прогресс.

## Неприкосновенные продуктовые правила

- AI не добавляет факты, которых не сообщил пользователь.
- Любой сформированный AI текст остаётся редактируемым и требует подтверждения человека.
- Низкий рейтинг не скрывает задачу и не запрещает отклик.
- Рекомендации не ограничивают доступ к общему каталогу.
- Команды не назначаются автоматически.
- Решение о принятии или отклонении отклика всегда принимает бизнес.
- Персональные и чувствительные характеристики участников не используются.

## Текущая архитектура

- `soile-platform/dist/index.html` — структура приложения и диалоги.
- `soile-platform/dist/styles.css` — дизайн-система и адаптивная вёрстка.
- `soile-platform/dist/app.js` — данные, состояние, рейтинг, каталог, отклики и WebMCP.
- `soile-platform/.openai/hosting.json` — конфигурация публикации.
- `soile-platform/README.md` — запуск, архитектура и демонстрационный сценарий.

Проект использует HTML, CSS и JavaScript без фреймворка. Данные MVP сохраняются в `localStorage`. Не добавляйте зависимости или этап сборки без явной необходимости и согласования с командой.

## Параллельная работа трёх участников

Перед изменениями каждый участник обязан:

1. Проверить `git status` и последние коммиты.
2. Сообщить команде задачу и файлы, которые он планирует менять.
3. Убедиться, что эти файлы не заняты другим участником.
4. Работать в отдельной ветке и, по возможности, в отдельном Git worktree.

Рекомендуемое разделение зон:

- Участник 1: бизнес-логика, состояние, рейтинг и WebMCP в `dist/app.js`.
- Участник 2: интерфейс, адаптивность и доступность в `dist/index.html` и `dist/styles.css`.
- Участник 3: тестирование, интеграция, документация и публикация.

Это разделение можно менять, но одновременно один файл редактирует только один участник. Изменения общего контракта данных, названий классов, ID элементов, ключа `localStorage` или WebMCP API заранее согласовываются со всеми затронутыми участниками.

## Правила Git

- Одна задача — одна короткоживущая ветка.
- Используйте понятные имена веток: `feat/<тема>`, `fix/<тема>`, `docs/<тема>`.
- Делайте небольшие логические коммиты с понятным сообщением.
- Перед передачей работы обновите ветку относительно актуальной основной ветки и разрешите конфликты самостоятельно.
- Не переключайте ветку в общем рабочем каталоге, если его использует другой участник.
- Не переписывайте чужие изменения и не используйте `git reset --hard`, `git checkout -- <file>` или принудительную отправку без явного согласования.
- Не коммитьте временные файлы, `.sites-runtime`, локальные серверные журналы, архивы публикации, секреты и токены.
- Не изменяйте `project_id` в `.openai/hosting.json` без согласования.

## Требования к изменениям

- Сохраняйте существующий пользовательский сценарий и обратную совместимость сохранённых данных.
- Новое состояние должно сохраняться через единый объект приложения, а не через разрозненные ключи `localStorage`.
- При изменении структуры данных добавляйте безопасные значения по умолчанию или миграцию.
- Рейтинг должен оставаться прозрачным: пользователь видит критерии, вес и начисленные баллы.
- Видимый интерфейс и WebMCP-инструменты должны использовать одинаковое состояние и одинаковые правила валидации.
- Не добавляйте фиктивные возможности, неработающие кнопки и скрытые автоматические решения.
- Тестовые данные должны быть синтетическими и не содержать реальную персональную информацию.
- Не вставляйте секреты, токены и приватные URL в исходный код.

## Стиль кода

- Используйте семантический HTML и доступные названия элементов управления.
- Основной текст должен оставаться читаемым на мобильных и десктопных экранах.
- Все интерактивные элементы должны работать с клавиатуры и иметь заметное состояние фокуса.
- Используйте существующие CSS-переменные и компоненты оформления вместо локальных дубликатов.
- В JavaScript предпочитайте небольшие функции с одним назначением и ранние проверки входных данных.
- Экранируйте пользовательский текст перед вставкой в HTML.
- Не меняйте язык интерфейса с русского без отдельной задачи.
- Не проводите массовое форматирование файлов, не относящееся к текущей задаче.

## Обязательная проверка

Перед коммитом:

1. Выполните синтаксическую проверку:

   ```bash
   node --check soile-platform/dist/app.js
   ```

2. Запустите статический сервер из `soile-platform/dist`.
3. Проверьте отсутствие ошибок в консоли браузера.
4. Проверьте изменённый сценарий на десктопной и мобильной ширине.
5. Проверьте минимум два связанных сценария, которые могли быть затронуты.

Для изменений основного потока дополнительно проверьте:

- создание и восстановление черновика;
- пересчёт рейтинга;
- AI-уточнение и подтверждение;
- публикацию и сортировку каталога;
- отправку отклика;
- ручное принятие и отклонение;
- сохранение состояния после перезагрузки;
- корректную работу соответствующих WebMCP-инструментов.

## Критерии готовности

Задача считается завершённой, когда:

- выполнены требования задачи;
- не нарушены продуктовые правила;
- нет ошибок JavaScript и сломанных элементов интерфейса;
- проведены обязательные проверки;
- документация обновлена, если изменились запуск, данные, рейтинг, архитектура или демонстрационный сценарий;
- коммит содержит только относящиеся к задаче файлы;
- участник передал команде краткое описание изменений, результаты проверки и возможные риски.

## Разрешение конфликтов

- Сначала определите назначение обеих версий кода, затем объединяйте поведение; не выбирайте одну сторону автоматически.
- Автор изменения подтверждает корректность своих участков после разрешения конфликта.
- После конфликта повторно выполняется полная проверка затронутого сценария.
- Если изменение нарушает продуктовый контракт или требует смены архитектуры, остановите интеграцию и согласуйте решение всей командой.
